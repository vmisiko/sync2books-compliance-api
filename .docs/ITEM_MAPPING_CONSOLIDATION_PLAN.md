# Item Mapping Consolidation: Implementation Plan

## Goal

Reduce the two-place cognitive load in the compliance dashboard (map in Mapping Center, then fix again in Item Sync) by making each field live in exactly one place, based on whether it's actually rule-mappable:

- **Rule-mappable → Mapping Center**: Tax Mapping, Payment Method, Quantity Unit. Fix once per source, applies to every item that shares the source value.
- **Always item-specific → Item Sync only**: Packaging Unit, Item Classification Code, **and Product Type** (corrected during implementation — see Phase 2). No source data exists to build a rule from (packaging, product type) or no rule can be trusted at this taxonomy size (classification) — see [`ERP_ITEM_FIELD_MAPPING_CAPABILITY_MATRIX.md`](./ERP_ITEM_FIELD_MAPPING_CAPABILITY_MATRIX.md) for the field-by-field evidence this plan is built on. Product type specifically: neither QuickBooks nor Odoo has a source signal distinguishing Raw Material from Finished Product at all (not a matching-quality problem, an information problem), so there's no rule to define — it's a per-item default-and-confirm instead.

Read that doc first if you haven't — this plan assumes its conclusions.

## A key existing-code fact that shapes this plan

The current Mapping Center "Classification" tab isn't a rule engine the way Tax/Payment are. Its backing entity (`ClassificationMappingOrmEntity`, created via `CreateMappingDto` with `type: 'classification'`, `sync2books-compliance-api/src/dashboard-mapping/presentation/dto/create-mapping.dto.ts:29-72`) bundles **four different fields into one row**: `itemClsCd`, `qtyUnitCd`, `pkgUnitCd`, and an optional `productTypeCode`, all matched together via `matchType` (`EXTERNAL_ID`/`SKU`/`NAME_CONTAINS`) + `matchValue` — i.e. a pattern-match rule ("items whose SKU starts with SEED- get this whole bundle"), not a closed-vocabulary rule like tax/payment.

There's also already a bulk-assign mechanism for this: `PATCH dashboard-api/mappings/bulk-classify` (`BulkClassifyMappingDto`, `dashboard-mappings.controller.ts:202-221`) applies one `itemClsCd` (+ optional `productTypeCode`) to a multi-selected set of `classification_mappings` row ids — this is what backs the checkbox column visible in the Mapping Center Classification tab today.

This matters because it means **quantity unit currently rides inside a mechanism built for classification**, even though `suggestUnitMapping` (`mapping-suggestion.service.ts:294-322`) already does true closed-vocabulary matching internally, structurally identical to `suggestTaxCodeMapping`/`suggestPaymentMethodMapping`. The plan below promotes quantity unit (and adds product type) to first-class rule types alongside tax/payment, and narrows the old pattern-matched "classification" mechanism down to just the two fields that actually need it — then relocates *that* mechanism's UI entry point to Item Sync, where bulk-assigning classification/packaging by SKU pattern is genuinely useful (fix many at once) without pretending it's a source-value rule.

## Phases

Ship in this order — later phases depend on earlier ones being live, not just designed.

### Phase 0 — Fix the classification-combobox false-default risk (standalone, no dependencies) — ✅ shipped

Independent bug, ship any time, ideally first since it's a data-integrity issue:

- `Next-Sync-2-books-compliance-dashboard-ui/components/kra/item-classification-combobox.tsx` fired an unsearched fetch sorted `itemClsCd ASC` the moment the combobox opened. A user who saved without typing a search term submitted `itemClsCd 1000000000` ("Live Plant and Animal Material...") against whatever item they had open — confirmed as the source of the flour-item screenshot from this investigation.
- **First attempt (reverted)**: required a typed query before showing anything selectable. Wrong call — most users don't know KRA's classification terminology well enough to search for it, so this blocked the common case instead of fixing the risky one.
- **Shipped fix**: kept the eager browse-on-open (no search required), but changed the *sort order* of the unsearched list — `search-item-classifications.usecase.ts` now orders by `itemClsNm ASC` instead of `itemClsCd ASC`. The default list is now alphabetically-by-name and scannable (recognizable category names to scroll through) instead of an arbitrary numerically-first code that happened to be irrelevant to whatever the user was actually classifying. Search remains available and unchanged for anyone who knows what to look for.
- Not pursued (flagged for later if the team wants better browsing): true hierarchical drill-down using `itemClsLvl` (1=broad category … 5=most specific) — the search endpoint already supports filtering by `itemClsLvl`, but `OscuItemClassificationOrmEntity` has no `parentCd`/hierarchy link, only the level number, so building a real drill-down (broad category → narrow down to a leaf code) would need either a derived parent relationship or new backend work. Worth a dedicated look if alphabetical-by-name browsing still isn't good enough at ~thousands of rows.

### Phase 1 — Quantity Unit: promote to a real rule type — ✅ shipped (backend)

What actually shipped differs from the original guess above in two important ways discovered during implementation — both documented in code comments at the relevant spots, summarized here so the history isn't lost:

1. **`KNOWN_UNITS`/`suggestUnitMapping` (the thing this phase was originally going to "expand") was dead code** — zero callers anywhere in `src`, confirmed by grep. The real live matcher was `DashboardMappingApplicationService.matchKraCode()`, which already queried the full real `oscu_codes` table (exact + SQL `LIKE` fuzzy fallback) — the gap was matching *quality* (no synonym/spelling normalization: "Kilograms" doesn't `LIKE`-match "Kilo-Gramme"), not table size. The dead table also had a confirmed-wrong pairing (EA/EACH/PCS → `NO`) — per the OSCU spec's real Unit of Quantity list (`.docs/OSCU_Specification_Document_v2.0.txt` §4.7, ~30 codes), "Pieces/item" is actually `U`; `NO` is the distinct code "Number". Good thing it was never wired in.
2. **A shared `unit_mappings` table existed before and was deliberately dropped** (commit `7d0e242`, "Split qtyUnitCd/pkgUnitCd into independent per-item KRA mappings, drop unit_mappings") — because it bundled qty+packaging into one row and silently defaulted packaging as a side effect of a qty match. That's a real, valid objection, but it's an objection to the *bundling*, not to shared-category resolution for qty alone. Re-verified against the OSCU spec that the qty code list is ~30 entries (small, closed vocabulary, same shape as tax/payment) before deciding to reintroduce a qty-*only* table that never touches `pkgUnitCd`.

**Shipped:**
- `unit-mapping.orm-entity.ts` — new `UnitMappingOrmEntity` (`unit_mappings` table), mirrors `TaxMappingOrmEntity` exactly (unique `(merchantId, internalUnit, active)` index, same dashboard-review fields), qty-only.
- `mapping-suggestion.service.ts` — dead `KNOWN_UNITS`/`UnitMappingSuggestion`/`suggestUnitMapping` removed; replaced with `QTY_UNIT_ALIASES` (~27 verified bucket entries covering common ERP phrasings, cross-checked against the real spec) and `suggestQuantityUnitAlias()`, which returns a *search term* to feed the live DB lookup — never a hardcoded final code, so a KRA resync/renumbering self-corrects instead of going stale. A caught-by-test bug along the way: bare single-letter aliases (`'g'`, `'l'`, `'m'`) false-matched almost anything in the loose contains-pass (e.g. `"gigawatt".includes('g')`) — fixed by restricting that pass to aliases ≥3 characters.
- `dashboard-mapping.application.service.ts` — `resolveQuantityUnit()`/`upsertUnitMapping()`/`activateUnitRow()`/`unitRowToListItem()` added, mirroring the tax pattern; `pullClassifications` now resolves qty through this shared row (an approved row always wins over a fresh pull's guess); full CRUD dispatch (`list`/`approve`/`update`/`createManual`/`findRowById`/`parseTypeFilter`) extended for the new `'quantity_unit'` type.
- `create-mapping.dto.ts`/`update-mapping.dto.ts` — `'quantity_unit'` added as a valid `type`, plus `internalUnit`.
- Test coverage includes one specifically proving the "fix once, apply to many" value: two items sharing an unrecognized raw unit label both resolve `null` on first pull; a human fixes the *one* shared `unit_mappings` row; a re-pull resolves *both* items from that single fix.

**Deliberately not done in this pass** (kept the change scoped to what's needed for correctness, not maximal):
- `ClassificationResolverTypeOrm`/`register-item.usecase.ts` were **not** touched — `classification_mappings.qtyUnitCd` is still a snapshot written at pull time, not a live cross-reference (unlike `resolvedInternalTaxCategory`→`resolvedTaxTyCd` for tax). This means fixing a shared `unit_mappings` row does not *instantly* update already-pulled items — it takes a re-pull, consistent with the existing re-pull-to-refresh pattern this module already uses for tax/payment. If instant propagation matters later, add a `resolvedInternalUnit` column + live cross-reference in `clsRowToListItem`, mirroring the tax pattern exactly.
- Frontend (Mapping Center Quantity Unit tab) is Phase 3's job, not this phase's — the backend is ready for it (`GET dashboard-api/mappings?type=quantity_unit` already works).

### Phase 2 — Product Type: default-and-confirm — ✅ shipped (frontend only — no rule type needed)

Turned out simpler than planned, and in a good way: this repo already had a well-designed per-item mechanism for exactly this ("needs confirmation before KRA sync"), so nothing new needed building on the backend.

**What was already there** (`catalog-item.entity.ts`): `CatalogItem.productTypeCode: string | null` is "the single source of truth for what kind of item this is," with `needsProductType` (`= productTypeCode === null`), `isStockItem`, and `deriveItemType` all *derived* from it and guarded by a doc comment saying these three functions are the only place allowed to derive anything from `productTypeCode`, specifically so they can never drift out of sync. `needsProductType` already **blocks KRA sync entirely** (`sync-items.usecase.ts`'s eligibility filter) until a human sets a real value — this is a stronger, cleaner gate than the `MappingStatus`-based "needs confirmation" state the original plan considered building; no new status value needed.

**Why no backend change**: `standardized-item.mapper.ts`'s `deriveProductTypeCode` deliberately returns `undefined` (not a guess) for anything but a confident Service signal — its doc comment says "NEVER guess a value here... fabricating data KRA requires a human to actually decide." Making the *backend* default to `'2'` would set `productTypeCode` for real at pull time, flip `needsProductType` to `false`, and let the item sync to KRA without anyone actually confirming — exactly the silent-promotion the original plan said not to do. Left untouched on purpose.

**What shipped — frontend only**, changing what's *pre-filled* in the edit form, not what's persisted:
- `add-item-drawer.tsx`'s `itemToFormValues()`: was `productTypeCode: item.productTypeCode` (a `string | null` value silently assigned into a non-nullable `FormValues.productTypeCode: string` field — a latent type bug, `next.config.mjs`'s `ignoreBuildErrors: true` was masking it). A pulled goods item opened Edit with a blank/unselected dropdown and a disabled Save button. Now defaults to `"2"` when null, matching `EMPTY_FORM`'s existing default for a brand-new manual item — same default, applied consistently to both create and edit.
- `mapping-content.tsx`'s `ClassificationDrawer`: same fix, `setProductTypeCode(row.productTypeCode ?? "2")` instead of `?? ""` (which rendered "Unspecified").
- Both still require an explicit Save click to actually persist — `productTypeCode` stays `null`/`needsProductType` stays `true` on the backend until then, so the compliance gate is untouched. This is the same principle Phase 0's fix landed on after the first attempt overcorrected: a visible, editable, easily-changed default is fine; what's not fine is a value a user can end up with *without* deliberately choosing it.
- One caveat not fully chased down: `ClassificationDrawer` is reused for any `classification_mappings` row a user opens, and that row's `productTypeCode` field is documented on the entity as a rule *scope filter* (null = "applies to all product types") when the row is a broader `NAME_CONTAINS` bulk rule rather than a single pulled item (`EXTERNAL_ID`-matched). Defaulting to `"2"` in that rarer case would narrow the rule's scope rather than just suggest "this item's type." In practice, every row this drawer is opened from today comes from the auto-pull placeholder flow (`suggestClassificationPlaceholder`, `EXTERNAL_ID`-or-equivalent per-item matching), so this doesn't bite currently — but worth a second look if Phase 4's relocated bulk-assign UI starts opening this same drawer for genuine multi-item `NAME_CONTAINS` rules.
- `CreateMappingDto` does **not** need a `'product_type'` type — there's no Mapping Center rule to create here; the field lives entirely on the per-item `CatalogItem`/`classification_mappings` row, edited in place.

**Not verified live**: no dev login credentials available in this session to screenshot the actual dropdown behavior in the browser. Verified statically instead — `tsc --noEmit` clean on both edited files (zero new errors), and the change reuses an already-proven code path (`EMPTY_FORM`'s existing `"2"` default) rather than introducing new logic.

### Phase 4 — Relocate classification/packaging bulk-assign into Item Sync — ✅ shipped

**Correction to the original plan, found before implementing**: the plan assumed the existing `bulk-classify` mechanism could just be relocated as-is ("already does the right thing... just surfaced in the wrong place"). That's not quite true — it operates on `classification_mappings` rows (`clsmap-...` ids), a completely different table from what Item Sync displays (`CatalogItem`/`catalog_items`, `item-...` ids). Bulk-approving a `classification_mappings` row only feeds into the actual registered item on the *next pull* (`DashboardItemsApplicationService.pullItems` looks up `clsRow?.itemClsCd` as an override at that time) — the same delayed "re-pull to refresh" pattern Phase 1 established for tax/quantity-unit. Moving that *button* into Item Sync without changing what it operates on would have selected `CatalogItem` rows in the UI but silently written to a different table, with no visible effect until a future pull. So this phase builds a **new, separate bulk mechanism that writes `CatalogItem` directly**, rather than relocating the existing one.

**Shipped, backend** (`sync2books-compliance-api`):
- `DashboardItemsApplicationService.bulkUpdateItems()` — loops the *existing*, already-battle-tested `updateItem()` (the same method the single-item "Edit Item" save already calls) over a list of item ids, collecting `{updated, skipped}`. No new business logic — `updateItem()` already handles both ERP-sourced (via `registerItem`'s upsert) and manually-created (via `updateManualItem`) items correctly; this just applies it to many ids at once, catching per-item failures into `skipped` rather than failing the whole batch (same convention as the old `bulkClassify`).
- `BulkUpdateItemsDto` + `PATCH dashboard-api/items/bulk-classification` — new DTO/endpoint, scoped to `classificationCode`/`packagingUnitCode`/`productTypeCode` (not name/sku/price/etc. — those don't make sense to bulk-apply identically across different items).
- The *old* `bulkClassify`/`BulkClassifyMappingDto`/`bulk-classify` endpoint on the mapping side is **left in place, untouched** — still functionally correct for its original purpose (bulk-approving `classification_mappings` placeholder rows), just no longer exposed via any UI after the frontend removal below. Not extended with `pkgUnitCd` as originally planned, since packaging now bulk-applies through the new `CatalogItem`-side mechanism instead.

**Shipped, frontend**:
- `item-sync-content.tsx` — new `BulkEditItemsModal` (classification/packaging/product-type, each field optional — blank means "leave unchanged" on every selected item), wired into the **existing** multi-select floating action bar (the "N selected" bar Item Sync already had for bulk-sync — no new selection UI needed, just a new "Bulk Edit" button next to "Sync to KRA"). Selection is already scoped to non-`REGISTERED` items only (`isSyncable`), matching the existing single-item "Edit Item" button's same restriction.
- `ItemsPloc.bulkUpdateItems()` / `ItemsRepository.bulkUpdateItems()` / `IItemsRepository` — new methods mirroring the existing `updateItem` plumbing, calling the new endpoint.
- `mapping-content.tsx` — **removed** the old classification-tab-only "Assign Classification (N)" bulk button and `BulkAssignClassificationModal` entirely (not hidden — deleted, per this codebase's "delete confirmed-unused code" convention), including the now-unused `onBulkClassify` prop threaded through all four `MappingTable` call sites and the now-unused `Tags` icon import. The **generic** checkbox-select + bulk-*approve* mechanism (`selected`, `selectedApprovable`, the "Approve N Mappings" button) is untouched and still serves all four tabs, including the new Quantity Unit tab — only the classification-specific bulk-*assign* action moved.

**Verification**: backend — `tsc --noEmit` clean, full suite still 22/22 test files, 171/171 tests passing (no new tests added for `bulkUpdateItems` itself; there's no existing test harness for `DashboardItemsApplicationService` to extend the way Phase 1 had one for `DashboardMappingApplicationService`, and the method is a thin loop over the already-tested `updateItem`, so a from-scratch NestJS TestingModule setup for one thin wrapper wasn't judged worth the cost here — flag if that judgment call should be revisited). Frontend — `pnpm exec tsc --noEmit` clean (only the 2 pre-existing unrelated errors). `pnpm run lint` / `eslint` could not be run in this session — the dependency isn't installed in this environment (`sh: eslint: command not found`), a pre-existing environment gap unrelated to this change — so unused-import-style issues were checked manually via `grep` instead of automated lint. No live browser verification (still no dev login credentials available in this session).

### Phase 5 — Import Ready / Not-Ready triage — ✅ shipped

**A significant, unplanned finding, discovered before implementing**: investigated where "ready" items would actually need to be surfaced (`items/pull`, per the original plan), and found `ClassificationResolverTypeOrm.resolveClassification()` throws unconditionally when `unitCode`/`packagingUnitCode` are missing — with **no fallback to unit_mappings or anywhere else**, despite Phase 1 building exactly that fallback into the Mapping Center pull path. `items/pull` only supplies those fields from an `active: true` (fully human-approved) `classification_mappings` row. Since `itemClsCd` is never auto-suggested, that row can only become active after a human manually fills it in — meaning **an item with no approved classification today doesn't get a pending/partial `CatalogItem` row via `items/pull` at all. It fails silently**: an error string lands in `pullItems()`'s `results[]`, and confirmed via `grep` that Item Sync's frontend doesn't display that array anywhere — only a bare toast count. Phase 1's quantity-unit automation doesn't unblock this, because `itemClsCd` remains the hard gate regardless of how good tax/qty-unit matching gets.

That ruled out the original framing ("Ready = made it into Item Sync, just needs cleanup") — for most fresh pulls, items don't make it into Item Sync at all yet. Also dropped **product type** from the Ready/Not-Ready definition entirely, consistent with Phase 2/3: there's no Mapping Center rule for it, so it can't participate in a "rule gap" framing — an item is never "not ready" because of product type, only because of tax or quantity unit. The **silent pull-failure gap itself is a separate, real product issue** (an item stuck behind an unapproved classification just vanishes from `items/pull` instead of appearing as a partial/pending row) — not fixed here, since it's a change to `registerItem`'s required-fields contract, not a triage-view addition. Worth a dedicated look.

**Scope actually shipped**: Ready/Not-Ready computed on the **Mapping Center side** (`classification_mappings`), where the gap is genuinely actionable — `ready = <tax resolves to an active tax_mappings row> && <quantity unit resolves, via the Phase 1 unit_mappings mechanism>`. This directly answers the real question: does this item need a *new Mapping Center rule*, or just the routine always-manual per-item work (classification code + packaging, handled in Item Sync per Phase 4)?

**Shipped, backend** (`sync2books-compliance-api`):
- `pullClassifications()` now resolves each item's real `resolvedTaxTyCd` (via the existing `resolveTaxTyCdForCategory` helper, cached per pull the same way `list()` already does) alongside the Phase-1 quantity-unit resolution, and computes `ready = !!resolvedTaxTyCd && !!qtyUnitCd` per item. The pull result gains aggregate `ready`/`notReady` counts alongside the existing `attempted`/`needsReview`.
- `clsRowToListItem()` computes the same `ready` boolean on every classification row returned from `list()`/`GET dashboard-api/mappings`, not just at pull time — so it stays visible on rows fetched later, not only in the pull-moment response.
- `MappingListItem.ready?: boolean` added; also corrected a stale doc comment on that interface still claiming qtyUnitCd has "no category table backing them anymore" — no longer true as of Phase 1.

**Shipped, frontend**:
- New pull-result banner in `mapping-content.tsx` (mirrors the existing tax-unmapped alert) showing "`N` of `M` pulled items have tax and quantity unit already resolved... `K` items still have no match — that's a Mapping Center rule gap, check the Tax Mapping and Quantity Unit tabs."
- Per-row "Needs rule fix" badge (with an explanatory tooltip) on classification rows where `ready === false`, so the signal stays visible when browsing the Classification tab later, not just right after a pull.
- `MappingListItem.ready`, `PullClassificationResultItem`, `PullClassificationsResult` added to the frontend `Mapping.ts`, and `PullMappingsResult.classifications?` typed to match `POST /mappings/pull`'s actual (previously untyped-on-frontend) response shape.

**Verification**: backend — added a dedicated test proving `ready` is computed correctly (true only when *both* tax and quantity unit resolve, independent of classification/packaging/product type) at both the pull-result and `list()` level; full suite 172/172 passing, `tsc --noEmit` clean. Frontend — `pnpm exec tsc --noEmit` clean (same 2 pre-existing unrelated errors). No live browser verification (no dev credentials this session, consistent with every prior phase).

This completes all originally-planned phases (0 through 5).

## Post-Phase-5: live testing incident and full `classification_mappings` removal (2026-08-27)

After Phase 5 shipped, live UI testing against a real go-live-certified org surfaced two problems that changed the plan's direction from "narrow the Classification tab" (Phase 3's stated non-goal) to "remove it entirely."

**The incident.** While testing the pull/register flow end-to-end, a "Pull from ERP" click in Item Sync silently overwrote 5 already-KRA-REGISTERED items' classification/unit/packaging/productType fields with blanks and downgraded their status back to PENDING. Root cause: `registerItem` resolved missing fields to `null` on every re-pull with no fallback to the existing row's already-good data, combined with a `classification_mappings` deletion (from an earlier data-reset step in this same testing session) that removed the row `items/pull` needed to resolve those fields. The 5 items' exact original data was recovered read-only via KRA's own `getItemInfo` OSCU lookup and restored.

**The decision.** Fixing the immediate bug (`registerItem` must prefer `existing.X` over a null resolution — see `register-item.usecase.ts`) was necessary but not sufficient: the underlying reason a re-pull could ever resolve `null` at all was that `classification_mappings` was still the mechanism `items/pull` depended on, months after Phase 4 had already given Item Sync its own direct-write path (`bulkUpdateItems`/`updateItem`) for the exact same fields. Keeping both mechanisms alive was the actual defect — two independent write paths to the same data, one of them (the pull-time placeholder-row path) fragile and a second source of truth. Decision: remove `classification_mappings` entirely rather than keep patching around it.

**What changed, backend (`sync2books-compliance-api`):**
- `register-item.usecase.ts` — `registerItem` now falls back to `existing.X` (never a blank/null) whenever a resolution comes back empty, for every classification-adjacent field. `taxTyCd` is the one exception, left throwing on failure since `tax_mappings` should always resolve via merchant/global default and a hard throw safely leaves `existing` untouched rather than risking a different kind of silent bad write.
- `classification-resolver.port.ts`/`classification-resolver.typeorm.ts` — the entire `EXTERNAL_ID`/`SKU`/`NAME_CONTAINS`/`DEFAULT` auto-match chain removed. `ClassificationMethod` is now just `'EXPLICIT' | 'UNRESOLVED'`. Only `tax_mappings` resolution remains a real lookup; classification/unit/packaging/product-type are now always supplied directly by the caller (Item Sync's own writes) or resolve to null/UNRESOLVED — never guessed from a stored rule.
- `classification-mapping.orm-entity.ts` deleted; `ClassificationMappingOrmEntity` removed from `app.module.ts`'s entity list, `oscu-mapping.module.ts`, `catalog.module.ts`, `dashboard-mapping.application.service.ts`'s constructor.
- `dashboard-mapping.application.service.ts` — `pullClassifications` (creating a placeholder row per pulled item) replaced by `computeItemReadiness`, a pure tally: still resolves tax + quantity unit per item (reusing `resolveTaxTyCdForCategory`/`resolveQuantityUnit`, so the `unit_mappings` "fix once, apply to many" behavior from Phase 1 is unchanged) and returns aggregate `{attempted, ready, notReady}` — but creates no per-item row at all, since there's nothing left for it to write to. `bulkClassify`, `clsRowToListItem`, `upsertClassificationPlaceholder`, `list()`'s classification branch, and `'classification'` all removed from `MappingType`.
- `mapping-suggestion.service.ts` — `suggestClassificationPlaceholder`/`ClassificationPlaceholder` removed (no longer has anything to suggest a placeholder for).
- `dashboard-mappings.controller.ts` — `PATCH .../bulk-classify` endpoint removed. `GET .../item-classifications` and `GET .../codes` stay — they're read-only KRA reference-data proxies, still the typeahead backing for Item Sync's own Edit Item classification/unit comboboxes, never `classification_mappings`-backed.
- `create-mapping.dto.ts`/`update-mapping.dto.ts`/`bulk-classify-mapping.dto.ts` (deleted) — classification-only fields (`matchType`, `matchValue`, `itemClsCd`, `priority`) removed from the mapping DTOs; `qtyUnitCd` kept on both, since `quantity_unit` still needs it.
